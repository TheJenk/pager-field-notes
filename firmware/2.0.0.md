# What changed in firmware 2.0.0

Compared with 1.1.3, from the device's root filesystem and testing on hardware (November 2026).
"Verified" means it was reproduced on a real Pager. The official release notes ship on the device
at `/etc/changelog`.

## At a glance
- Same base: OpenWrt 24.10.1, kernel 6.6.86 (rebuilt). The only new package is the `blue5`
  Bluetooth scanner. **No new DuckyScript commands.**
- **Bluetooth recon** is now built in (`blue5`), and it takes over the adapter from BlueZ.
- **GPS is read natively by PineAP**, and gpsd is turned off by default.
- **Theme framework 0.9**: new screens for Bluetooth recon, GPS Advanced and a help page per
  settings menu.
- Much faster boot and menus. A rebuilt Virtual Pager (web UI) with recon tables, a WiGLE map and
  a file browser.
- Updating regenerated the SSH host key (expect a host-key warning) and removed installed user
  payloads. Loot and installed themes were kept.

## Bluetooth: blue5 — *verified*
- A `blue5` daemon owns `hci0`, and its init script **stops `bluetoothd`**. `bluetoothctl`
  scanning, `hcitool lescan` and `btmgmt` therefore don't work by default. Don't restart
  `bluetoothd` from a payload: it would break the Pager's own BT recon.
- Read results with **`blue5ctl fetch`**: `-n 0` for all pages, `-g S` for devices seen in the
  last S seconds, plus filters such as `-N name`, `-o 0xID` (company), `-r` (no random
  addresses) and `-d MAC`. The output is a fixed-width table:
  `ADDRESS TYPE PWR AVG MIN MAX TX PKTS FIRST LAST INFO NAME`.
  - INFO holds `co 0xXXXX` (Bluetooth company ID).
  - NAME holds the device name followed by `svc=XXXX,YYYY` (16-bit service IDs), `mfr=<hex>`
    and `sd=<hex>` (service data). 128-bit UUIDs are not shown.
- Other commands: `blue5ctl status`, `ping`, `clear`, `new`/`end` (database scans),
  `wigle on|off`, and `scan …` (change scan settings live).
- Devices are logged to SQLite at `/root/recon/blue5.db` (table `bt_device`, flushed every 30 s;
  `sqlite3` is on the device). Settings live in `/etc/config/blue5`.
- Local API: `recon/bluetooth/status`, `recon/bluetooth/devices` (paged JSON with vendor and
  company names) and `recon/bluetooth/devices/{mac}`.

## GPS: native in PineAP — *verified*
- `pineapd` opens the receiver itself (`uci pineapd.@pineapd[0].pineapgps=1` and `gpsdevice`),
  detects the baud rate and receiver type, and stops gpsd. `gpsd.core.enabled` is `0`, so
  **`gpspipe` returns nothing** unless gpsd is switched back on (Settings > GPS > Advanced, or
  `GPS_CONFIGURE GPSD …`).
- Read the position from the local API: `pineap/gps/get` returns JSON with `lat`, `lon`, `alt`,
  `speed`, `fix`, `hprecision`, `connected`, `baud`, `sats_tracked`, `signal_quality` and
  `readiness`. It answers in about 30 ms. `fix` ≥ 1 with `connected: true` means the position is
  usable. `GPS_GET` wraps the same call (prints `lat lon alt speed`; much slower).
- **`GPS_CONFIGURE` changed:** it now takes a mode first. Use `GPS_CONFIGURE PINEAP [serial]` or
  `GPS_CONFIGURE GPSD [serial] [speed]`. The old `GPS_CONFIGURE [serial] {speed}` form prints
  usage.
- `GPS_LIST` reads PineAP's GPS device when gpsd is off.

## Wi-Fi — *verified*
- PineAP runs two monitor interfaces: one on the tri-band USB radio (hopping 2.4 and 5 GHz) and
  one on the built-in 2.4 GHz radio, which stays parked; retuning it returns "Resource busy".
- **Passive `tcpdump -i <mon> -e -n -l type mgt` on those interfaces works** and doesn't disturb
  recon. It's the least intrusive way for a payload to watch Wi-Fi on 2.0.
- `PINEAPPLE_SET_BANDS <iface> 2` returned success, but the radio kept hopping 5 GHz in a quick
  test.
- New local API routes: `recon/wifi/status` (packets per second, totals, encryption and frequency
  breakdowns), `recon/wifi/devices` (paged), `recon/wifi/devices/{mac}/clients`,
  `recon/wifi/count` and `recon/setup` (WiGLE, GPS and Bluetooth settings).

## Themes: framework 0.9 — *verified*
See [theme firmware notes](../themes/firmware-notes.md#firmware-200--theme-framework-09) for the
full list. In short, a 1.1.x theme still runs, but:
- the UI shows a "missing required components" warning and a "different theme engine version"
  warning at every start;
- the new screens are borrowed from the stock theme and draw **without a status bar**;
- the GPS status icon falls back to its old `off` state.

## Still true from 1.1.3
- The USB serial hotplug script that leaves dangling `/dev/serial/by-path` links is unchanged, so
  expect the same stale-device behaviour (not re-tested).
- Launching a payload from a theme item was not re-tested on 2.0.

## Porting a 1.1.x payload
Detect at start and support both:

```sh
# GPS
if curl -s --unix-socket /tmp/api.sock http://localhost/api/pineap/gps/get | grep -q '"connected"'; then
    GPS=api       # poll pineap/gps/get
elif [ -c "$(uci -q get gpsd.core.device)" ]; then
    GPS=gpsd      # gpspipe -w
fi
# Bluetooth
if command -v blue5ctl >/dev/null && blue5ctl ping >/dev/null 2>&1; then BLE=blue5; else BLE=bluez; fi
# Wi-Fi: list existing monitor interfaces first; only create your own if there are none
iw dev | awk '/Interface/{i=$2} /type monitor/{print i}'
```
